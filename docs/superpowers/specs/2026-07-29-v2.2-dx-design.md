# laravel-onesignal v2.2 — DX Design: derived resync + lazy manager reads

**Date:** 2026-07-29
**Issue:** [Multek-Company/laravel-onesignal#12](https://github.com/Multek-Company/laravel-onesignal/issues/12)
**Status:** Approved by Rodrigo (brainstorming session 2026-07-29)

## Context

Both gaps are package knowledge leaking into every consuming app, surfaced by
corbi's PR #211 review.

Corbi's observer today hand-maintains a nine-element `ONESIGNAL_FIELDS` array
mirroring what our `getOneSignal*()` getters read, plus a `wasChanged()` guard,
plus an enablement check, plus queue resolution. The enablement check and queue
resolution are already ours as of [#11](https://github.com/Multek-Company/laravel-onesignal/issues/11).
This spec removes the remaining two, and with the shipped observer the whole
class disappears — corbi's `UserObserver` becomes one attribute on the model.

Separately, `OneSignalManager` snapshots `enabled`/`appId`/`trackEvents` into
constructor properties at first resolution, so any later `config()->set()` is
invisible.

## Decisions (from brainstorming)

1. **`oneSignalWatchedAttributes()` is rejected.** The issue proposed a declared
   attribute list on the trait. It does not solve the bug the issue was filed
   about: a hand-maintained list can still be outrun by a new tag, whether it
   lives in the app's observer or in our trait. Moving it shortens the distance
   to the getters; it does not pin anything. Shipping it would mean writing a
   changelog entry that implies a guarantee we do not provide.
2. **Resync is decided by diffing the payload, not the attributes.** Correct by
   construction for the user's own saves: any new tag, getter override, or
   `default_tags` change is covered the day it lands, with no list to maintain.
3. **The package ships `OneSignalObserver`.** App-side integration becomes one
   attribute: no field list, no `wasChanged()` guard, no enablement check, no
   queue lookup. `toOneSignalPayload()` and `oneSignalPayloadChanged()` are also
   public, so apps with their own observers can use the predicate without taking
   ours.
4. **`#[ObservedBy]`, never trait auto-boot.** A `bootHasOneSignal()` that wired
   `saved`/`deleted` would make `use HasOneSignal` silently start queueing jobs
   on every save — a behavior break for v2.1 users, invisible at the call site.
   The attribute is opt-in by construction, greppable, and idiomatic Laravel 11+.
5. **The observer's boundary is documented, not implied.** It covers the user's
   own saves. Relation-derived tags going stale is structurally undetectable from
   those events, and mass updates bypass events entirely — so the README states
   the boundary, shows the related-model observer pattern, and recommends
   scheduling `onesignal:backfill` as the reconciliation net. This was the one
   condition for shipping the observer at all: having rejected the
   watched-attributes list for implying a guarantee it could not keep, an
   observer behind a one-line opt-in must not repeat that in the docs.
6. **Two independent PRs.** Part B (manager) is settled and unblocked; it does
   not wait on Part A.

## Verified facts this design rests on

Checked against `vendor/laravel/framework` in this worktree (Laravel 12):

- `Model::finishSave()` fires the `saved` event **before** calling
  `syncOriginal()` ([Model.php:1477-1486](../../../vendor/laravel/framework/src/Illuminate/Database/Eloquent/Model.php)).
  So inside a `saved` hook, `getOriginal()` still holds pre-save values. On
  insert the original is empty, so a new user diffs as changed and syncs.
- `setRawAttributes()` clears both `classCastCache` and `attributeCastCache`
  ([HasAttributes.php:2063-2075](../../../vendor/laravel/framework/src/Illuminate/Database/Eloquent/Concerns/HasAttributes.php)).
  So a clone rehydrated from the original state will not serve stale values for
  custom-cast or `Attribute`-accessor fields.
- `Relation::touch()` issues a `rawUpdate()` — a query-builder update that fires
  **no** model events ([Relation.php:220-240](../../../vendor/laravel/framework/src/Illuminate/Database/Eloquent/Relations/Relation.php)).
  So Eloquent's `$touches` cannot be used to propagate a related row's change
  into a user-side `saved` hook. This is why decision 5 exists.
- `isForceDeleting()` is still `true` while the `deleted` event fires during a
  force delete, so one `deleted` handler distinguishes a soft delete from a force
  delete without a separate `forceDeleted` hook.
- `SerializesModels` stores a `ModelIdentifier` (class + key + loaded relation
  names), and `restoreModel()` re-queries with
  `->useWritePdo()->firstOrFail()->loadMissing($relations)`
  ([SerializesAndRestoresModelIdentifiers.php:108-113](../../../vendor/laravel/framework/src/Illuminate/Queue/SerializesAndRestoresModelIdentifiers.php)).
  So `SyncUserToOneSignal` builds its payload from current database state at
  execution time, on the write connection, with relations freshly resolved —
  never from a dispatch-time snapshot, and never from a lagging read replica.
- A missing model on restoration fails the job unless `deleteWhenMissingModels`
  is in the payload ([CallQueuedHandler.php:307-318](../../../vendor/laravel/framework/src/Illuminate/Queue/CallQueuedHandler.php)).
  This drives A5.

If any of these change in a future Laravel major, the affected tests below fail
loudly rather than silently mis-syncing.

# Part A — derived resync

## A1. Extract `toOneSignalPayload(): array`

The payload is currently assembled inline inside `syncToOneSignal()` with
`array_filter` gymnastics. Extract it:

```php
public function toOneSignalPayload(): array
{
    $tags = $this->getOneSignalTags();
    $properties = array_filter([
        'language' => $this->getOneSignalLanguage(),
        'timezone_id' => $this->getOneSignalTimezone(),
        'country' => $this->getOneSignalCountry(),
    ], fn ($value) => $value !== null);

    ksort($tags);
    ksort($properties);

    return [
        'external_id' => $this->getOneSignalExternalId(),
        'tags' => $tags,
        'properties' => $properties,
        'email' => $this->getOneSignalEmail(),
        'phone' => $this->normalizedOneSignalPhone(),
    ];
}
```

`syncToOneSignal()` becomes build-then-send. This is a clarity win independent
of the diff: the payload becomes a named, directly testable unit, and apps that
want custom change detection can diff it themselves.

`ksort` on tags and properties makes comparison order-insensitive. The current
implementation builds tags in config order, so ordering is already stable — this
is insurance against an override returning arbitrary order, at negligible cost.

## A2. Move the phone warning to the send path

`validatedOneSignalPhone()` logs a warning for a non-E.164 phone. Building the
payload twice per save would double that log line and break the existing
`Log::shouldReceive('warning')->once()` assertion in
`tests/Feature/HasOneSignalTest.php`.

Split validation from reporting:

- `normalizedOneSignalPhone(): ?string` — silent. Returns the phone if E.164,
  `null` otherwise. Used by `toOneSignalPayload()`.
- `syncToOneSignal()` logs the warning when `getOneSignalPhone()` is non-null
  but normalizes to `null`.

Net effect: the warning still fires exactly once per actual sync, so observable
behavior and the existing test are unchanged. `validatedOneSignalPhone()` is
removed — it is `protected`, so this is not a public BC break.

The payload therefore carries exactly what gets sent, with no diff-only variants.

## A3. `oneSignalPayloadChanged(): bool`

```php
public function oneSignalPayloadChanged(): bool
{
    $current = $this->oneSignalPayloadFrom($this->getAttributes());
    $previous = $this->oneSignalPayloadFrom($this->getOriginal());

    if ($current === $previous) {
        return false;
    }

    Log::debug('OneSignal payload changed', [
        'external_id' => $current['external_id'],
        'changed' => array_keys(array_diff_assoc(
            array_map('serialize', $current),
            array_map('serialize', $previous),
        )),
    ]);

    return true;
}

protected function oneSignalPayloadFrom(array $attributes): array
{
    return (clone $this)
        ->setRawAttributes($attributes, sync: true)
        ->setRelations([])
        ->toOneSignalPayload();
}
```

**Both sides are built from clones with relations cleared.** This corrects the
first draft of this spec, which cleared relations only on the "previous" side.
That was wrong: if the app did `$user->load('role')` and then changed `role_id`,
the live model still holds the *old* loaded relation, so the "current" payload
would read the old role name, match the previous payload, and the resync would
be silently skipped — reintroducing the exact class of bug this design exists to
kill. Cloning both sides makes each one re-resolve relations against its own
foreign keys.

Cost: two extra queries per save, and only for apps whose tag closures walk
relations. Apps with plain attribute tags pay nothing but two clones.

Note the asymmetry this creates: `syncToOneSignal()` called directly on the live
model uses whatever relations are already loaded, while the diff always
re-resolves. That is intentional — a direct sync should send what the caller has
in hand.

The debug log is the readability paydown. Derived behavior is impossible to get
wrong but harder to introspect than reading a list, so "why didn't it sync?" is
answered in the log rather than in the reader's head. `serialize` before
`array_diff_assoc` because the payload has nested arrays.

## A4. `Multek\OneSignal\Observers\OneSignalObserver`

```php
class OneSignalObserver
{
    public function saved(Model $user): void
    {
        if ($user->oneSignalPayloadChanged()) {
            $user->syncToOneSignalAsync();
        }
    }

    public function deleted(Model $user): void
    {
        if ($this->softDeletes($user) && ! $user->isForceDeleting()) {
            return;
        }

        $user->deleteFromOneSignalAsync();
    }

    public function restored(Model $user): void
    {
        $user->syncToOneSignalAsync();
    }

    protected function softDeletes(Model $user): bool
    {
        return in_array(SoftDeletes::class, class_uses_recursive($user), true);
    }
}
```

- **`saved`** covers create and update in one handler. On create the diff runs
  against an empty original, so a new user always syncs. A `save()` that changes
  nothing OneSignal cares about dispatches nothing.
- **`deleted`** derives the soft-delete decision rather than leaving it as a
  caveat for the app. A reversible soft delete returns early and leaves the
  OneSignal profile intact; a force delete — where `isForceDeleting()` is still
  true during the same event — deletes. A separate `forceDeleted` handler is
  unnecessary and would double-dispatch.
- **`restored`** resyncs, so a soft-deleted-then-restored user is not left
  missing from OneSignal until the next backfill.

No enablement check: `syncToOneSignalAsync()` and `deleteFromOneSignalAsync()`
already gate on `isEnabled()`.

The `Model` type-hint is loose — the observer requires a model using
`HasOneSignal`. The package has no PHPStan config, so this is a docblock contract
(`@param Model&HasOneSignal $user`) rather than an enforced type. Attaching it to
a model without the trait fails with a clear `BadMethodCallException` on the
first save, which is acceptable.

## A5. `deleteWhenMissingModels` on `SyncUserToOneSignal`

`SyncUserToOneSignal` carries the model via `SerializesModels`, so restoration
re-queries and throws `ModelNotFoundException` if the row is gone — which fails
the job (see verified facts). With the observer dispatching on every save, the
create-then-delete race stops being theoretical: a user is created, the sync job
is queued, the user is deleted before a worker picks it up, and the job lands in
`failed_jobs`.

Add to the job:

```php
public bool $deleteWhenMissingModels = true;
```

Same reasoning as #11's 404 handling: a profile that no longer needs syncing
because the record is gone is a completed outcome, not a failure. The delete job
is unaffected — it takes a string.

## A6. README: the observer's boundary

The observer covers the user's own saves. That boundary must be stated, not
implied — it is the condition under which shipping it was acceptable at all.

| Case | Example | Covered? |
|---|---|---|
| (a) User's own attribute changed | `email` updated | Yes |
| (b) User's foreign key changed | `role_id` 1→2 in the same save | Yes, via A3's two-sided clone |
| (c) Related row's content changed | `roles.name` renamed, user untouched | **No** — no user-side event fires |
| (d) Many-to-many attach/detach | user gains a role | **No** — no user-side event fires |

(c) and (d) are structurally undetectable from the user's own events and cannot
be automated by us: `default_tags` closures are opaque to introspection, and
`$touches` fires no model events. A declared watched-attributes list misses them
equally — this is a limit of any user-side mechanism, not of the diff.

**Basic integration:**

```php
#[ObservedBy(OneSignalObserver::class)]
class User extends Authenticatable
{
    use HasOneSignal;
}
```

**Relation-derived tags need their own observer** — the documented answer to (c)
and (d):

```php
public function updated(Role $role): void
{
    if ($role->wasChanged('name')) {
        $role->users()->chunkById(500, fn ($users) => $users->each->syncToOneSignalAsync());
    }
}
```

`chunkById` bounds queue pressure. Batching would not reduce API calls —
OneSignal's `createUser` is one request per user regardless — which is why the
package adds no batch job for this.

**Reconciliation** — `onesignal:backfill` as a scheduled job, not an emergency
tool:

```php
Schedule::command('onesignal:backfill')->weekly();
```

The framing to state explicitly: an observer is incremental and best-effort, and
no observer catches everything — mass updates (`User::where(...)->update()`) fire
no events at all. Backfill is the reconciliation half. Together they are
complete; either alone is not.

What makes this safe rather than merely hedged: because the job rebuilds the
payload from the database at execution time, the diff is only a *dispatch filter*
— never the source of what gets sent. A missed (c)/(d) change is corrected in
full by the next sync from any cause, so the system converges instead of
accumulating drift.

**Escape hatches**, in increasing order of control: omit the attribute and
register the observer manually; write your own observer using
`oneSignalPayloadChanged()`; call `syncToOneSignalAsync()` by hand.

## A7. Tests (Part A)

Feature, mocked manager, following the existing `HasOneSignalTest` style:

1. `toOneSignalPayload()` returns external_id, tags, properties, email and phone
   for a fully-populated model.
2. `toOneSignalPayload()` sorts tags and properties by key.
3. `syncToOneSignal()` still sends exactly the payload contents — regression
   guard on the A1 extraction.
4. The non-E.164 warning still fires exactly once per sync (existing test, must
   stay green unmodified).
5. `oneSignalPayloadChanged()` is false when a save touched no OneSignal field.
6. `oneSignalPayloadChanged()` is true when a tag-mapped attribute changed —
   with **no watched-attributes list anywhere**, which is the whole point.
7. `oneSignalPayloadChanged()` is true for a never-saved model (empty original).
8. `oneSignalPayloadChanged()` is true when a relation-walking tag closure's
   foreign key changed **and the relation was eagerly loaded before the change**
   — the two-sided-clone regression test from A3. Would fail against the first
   draft of this design, so it is the highest-value test here.
9. Observer `saved` dispatches a sync on a real change, and nothing otherwise.
10. Observer `saved` dispatches on create.
11. Observer `deleted` dispatches a delete for a model without `SoftDeletes`.
12. Observer `deleted` dispatches nothing when a `SoftDeletes` model is soft
    deleted, and does dispatch on `forceDelete()`.
13. Observer `restored` dispatches a sync.
14. `SyncUserToOneSignal` declares `deleteWhenMissingModels`, asserted by
    dispatching onto the `database` queue connection and reading the serialized
    `payload` column — proving the flag reaches the payload
    `CallQueuedHandler` actually reads, not just the property.

Tests 8 and 12 need fixtures beyond the current `Tests\Fixtures\User`: a model
with a relation-closure tag, and a soft-deleting model. Both need real tables,
which is cheaper than the first draft of this spec assumed —
`tests/Feature/BackfillCommandTest.php` already creates a `users` table with
`Schema::create()` in a `beforeEach` and inserts rows, so Testbench's in-memory
SQLite is already working in this suite and the pattern to copy exists.
Everything else runs on `forceFill` as today.

# Part B — lazy manager reads

## B1. Config reads move into the manager

`isEnabled()`, `getAppId()`, and the track-events gate read `config()` at call
time. The derived rule currently in the provider —
`enabled && trim($appId) !== ''` — moves into `isEnabled()`, which also makes
CLAUDE.md's "the enabled gate lives inside `OneSignalManager`" literally true.

Constructor parameters become nullable **overrides** rather than snapshots:

```php
public function __construct(
    protected DefaultApi|Closure $api,
    protected ?string $appId = null,
    protected ?bool $enabled = null,
    protected ?bool $trackEvents = null,
) {}
```

`null` means "read config". This keeps direct construction working —
`new OneSignalManager($api, 'test-app-id', trackEvents: true)` appears twice in
our own `OneSignalManagerTest` and is plausible in consumer tests — while the
container path gets fully lazy behavior. No BC break.

## B2. The SDK client becomes lazy

The provider currently calls `$app->make(DefaultApi::class)` eagerly inside the
manager's factory closure, so merely asking `isEnabled()` builds a Guzzle
`HandlerStack`. Accept a `Closure` and memoize:

```php
public function api(): DefaultApi
{
    if ($this->api instanceof Closure) {
        $this->api = ($this->api)();
    }

    return $this->api;
}
```

Every internal `$this->api->…` becomes `$this->api()->…` — a mechanical sweep.
Because `skips()` returns before any API access, disabled mode never constructs
Guzzle at all.

Passing a mocked `DefaultApi` directly keeps working, so existing manager tests
are untouched.

## B3. Remove the `forgetInstance` dance

The five `app()->forgetInstance(OneSignalManager::class)` calls — two in
`ServiceProviderTest`, one in `BackfillCommandTest`, two in `HasOneSignalTest` —
become unnecessary and are deleted. Their removal is the acceptance signal for this
part: if a test still needs the singleton dropped to observe a config change,
Part B is not done.

## B4. Tests (Part B)

1. `config(['onesignal.enabled' => false])` after the manager is resolved makes
   `isEnabled()` return false, **without** `forgetInstance`.
2. Same for `app_id` set to empty → `isEnabled()` false.
3. Same for `track_events` toggled after resolution → `trackEvents()` respects
   the new value.
4. Constructor overrides still win over config for all three.
5. Resolving the manager and calling `isEnabled()` while disabled never resolves
   `DefaultApi` — assert via a container binding that records resolution.
6. Full existing suite green with every `forgetInstance` call removed.

## Out of scope

- **Automating cross-model invalidation** (cases c and d). Structurally
  impossible from the user's own events; the README pattern plus scheduled
  backfill is the answer.
- **Any config flag to disable the observer.** The `#[ObservedBy]` attribute *is*
  the opt-in.
- `OneSignal::deleteUserAsync()` on the manager. The public
  `DeleteUserFromOneSignal` job already covers deletion with no model in hand,
  and a facade path would give the enablement gate a second home.
- A batch sync job for cross-model invalidation. `chunkById` plus
  `syncToOneSignalAsync()` covers it without new API surface, and batching would
  not reduce API calls.
- Tenant-scoped `app_id` resolution. Part B makes runtime toggles *possible*
  (config is re-read per call), but multi-tenant credential switching is its own
  design.
- Changing the `SyncUserToOneSignal` job's model-based constructor. A5 only adds
  a property.

## Shipping order

1. **Part B first** — small, settled, no dependency on Part A. Removing the
   `forgetInstance` calls also makes Part A's tests cleaner to write.
2. **Part A second** — depends on #11's `deleteFromOneSignalAsync()` (already
   merged into this branch), which the observer's delete path calls.

Both target v2.2.0. Part A is additive; Part B is internal restructuring with no
public behavior change, so neither forces a major.
